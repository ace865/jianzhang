# 统一开发与版本规范

## 适用范围与平台状态

本规范适用于开发者、Codex、Claude 和其他开发工具。公共规则以本文件为准；工具入口和操作指南引用本文件。用户当前的明确指令优先，执行时记录与公共规则的差异。

简账的目标是使用 Flutter 支持 iOS 和 Android。当前仓库仅包含 Android 工程，已发布 Android 测试版；iOS 状态为“未实现”。新增规范不代表完成平台适配或验证。

## 产品与数据约定

简账保持离线个人账本定位，无账号和云同步。正式安装包首次启动为空账本，不预置演示账单。

保留 A 暖白陶土和 C 深色暖灰主题，首页右上角切换并持久化。分类图标使用同色线条，不增加圆圈或彩色底块。分类选中态使用文字下划线。

金额使用整数分，输入、存储和汇总避免浮点金额计算。结余表示所选期间收入减支出，支付方式仅用于标记账单。

数据库结构版本和备份格式版本分别管理，不跟随产品版本自动升级。修改结构或格式时，明确旧数据处理方式，提供保留数据的迁移和回归测试。大更新也必须保护已有账本；无法兼容时，提供可验证的数据迁移方案。

备份恢复先校验，再确认替换，在事务中写入。恢复失败保留原账本。修改备份逻辑时，验证完整往返、损坏输入和事务回滚。

## 跨平台开发

界面和业务逻辑优先放在共享 Dart 代码中。平台差异集中封装，页面调用共享接口，不直接调用原生平台接口。

新增或升级依赖前，检查 iOS 和 Android 支持范围、最低系统要求及许可。只有单平台支持的依赖，需要在平台封装中提供另一端实现，或明确功能限制。禁止依赖更新后才发现目标平台无法构建。

文件选择、备份恢复、安全区域、键盘、权限和应用生命周期需要分别验证。两端保留相同的账务计算与数据语义，系统交互按平台要求适配。

iOS 接入前，将相关检查标为“未实现”，不要宣称双平台验证通过。接入后，共享代码或依赖变化需检查两端。单平台修改检查对应平台及受影响的共享行为。

## 版本编号

产品版本使用 `主版本.次版本.修订版本`，iOS 和 Android 共用产品版本规则。一次发布包含多类变化时，按最高级别升级。升级某一位后，右侧数字归零。

| 类型 | 适用变化 | 示例 |
| --- | --- | --- |
| 大更新 | 重大产品重构、首次正式支持 iOS、不兼容变化 | `1.2.3 → 2.0.0` |
| 小更新 | 新增功能，保持已有数据和主要操作兼容 | `1.2.3 → 1.3.0` |
| 普通更新 | 问题修复、性能优化、界面细节和兼容性改善 | `1.2.3 → 1.2.4` |

新增 iOS 工程或实验性适配本身不代表正式支持。首次正式支持需要完成构建、真机验收和发布准备，再按大更新编号。

产品版本以 `pubspec.yaml` 为准。仅修改文档时，不升级应用版本、不增加构建号、不重新打包；开发中的每次提交也不必升级版本。发布新的应用构建时，确定版本并同步变更记录。

### 构建号与测试版

Flutter 版本字段使用 `产品版本+构建号`，例如 `1.2.4+8`。构建号为正整数，按项目已分配的最大值继续递增，不因产品版本变化而归零。每次新的分发构建分配新号，记录平台、源码提交和构建号；两端可使用不同构建号。

同一标签对应源码在另一平台构建或重新分发时，可使用 Flutter 的 `--build-number` 指定新构建号，并在发布记录中记录覆盖值。保持标签源码不变；应用代码或依赖发生变化时，升级产品版本或测试序号，创建新标签。

Android 将构建号映射为 `versionCode`。iOS 接入后，将构建号映射为 `CFBundleVersion`。覆盖升级时，检查平台实际输出的构建号高于已安装版本。

测试版本使用 `-alpha.N`、`-beta.N` 和 `-rc.N`。`rc` 表示 Release Candidate（候选发布版）。正式版移除测试后缀。

| 阶段 | 用途与进入条件 | 示例 |
| --- | --- | --- |
| `alpha` | 早期功能验证，功能可以未完成；已知缺陷和数据风险必须列明，只用于测试账本 | `1.3.0-alpha.1+8` |
| `beta` | 本次计划功能已实现，核心自动测试与对应平台构建通过；扩大测试范围，收集真机兼容性问题 | `1.3.0-beta.1+9` |
| `rc` | 本次发布功能冻结，必要真机验收完成，无已知阻断发布的问题；检查正式签名、覆盖升级和发布材料 | `1.3.0-rc.1+10` |
| 正式版 | 候选版验收通过，发布记录完整，移除后缀并重新检查最终构建 | `1.3.0+11` |

同一产品版本、同一阶段的序号从 1 开始递增，例如 `beta.1 → beta.2`。切换阶段或进入新的产品版本时，阶段序号从 1 开始；构建号始终递增。阶段由验证结果决定，符合后续阶段条件时可以跳过早期阶段，不能只改后缀宣称完成验收。

常见发布顺序为 `1.3.0-alpha.1+8 → 1.3.0-beta.1+9 → 1.3.0-rc.1+10 → 1.3.0+11`。候选版修复问题后发布 `rc.2`，并重新检查受影响行为；增加功能或出现重大问题时，恢复测试阶段并选择新的产品版本，例如 `1.4.0-beta.1`，避免版本排序倒退。

测试标签使用 `v1.3.0-alpha.1`、`v1.3.0-beta.1` 或 `v1.3.0-rc.1`。GitHub Releases 中，三个测试阶段均标记为预发布，正式版取消预发布标记。预发布只是验证阶段，不改变公开仓库的访问权限，也不授权应用商店或测试渠道分发。

当前已发布版本为 `1.0.0-beta.1+1`。这次只完善规范，保留现有版本、标签和安装包，不自动晋级为候选版或正式版。

iOS 的 `CFBundleShortVersionString` 使用三段数字，不写测试后缀。测试版构建时，从产品版本提取 `1.3.0` 作为平台构建版本；完整测试版本保留在发布记录中，使用测试分发渠道标明阶段。平台字段转换不能改写 `pubspec.yaml` 中的产品版本来源。

### 编号示例

| 发布内容 | 编号结果 |
| --- | --- |
| 修复备份失败，并优化输入框 | `1.2.3 → 1.2.4` |
| 新增报表，并修复旧问题 | `1.2.3 → 1.3.0` |
| 重大重构，同时新增功能和修复问题 | `1.2.3 → 2.0.0` |
| 首次正式提供 iOS 版本 | `1.2.3 → 2.0.0` |
| 只修改开发文档 | 保留现有产品版本与构建号 |
| 同一标签源码重新分发新构建 | 产品版本不变，增加构建号，如 `1.3.0-beta.1+9 → 1.3.0-beta.1+10` |

## 检查与验收

检查范围由修改内容决定，不要求纯文档修改构建应用。代码修改至少运行以下检查，并补充受影响行为的测试：

```sh
flutter pub get --enforce-lockfile
dart format --output=none --set-exit-if-changed lib test
flutter analyze --no-pub
flutter test --no-pub
```

| 修改或交付 | 必要检查 |
| --- | --- |
| 纯文档 | 链接、中文排版、事实和规则一致性，`git diff --check` |
| 共享代码或依赖 | 格式、静态检查、受影响测试和已接入平台构建 |
| 单平台代码 | 公共代码检查、对应平台构建和受影响功能验证 |
| 数据结构或备份格式 | 旧数据迁移、金额与关联完整性、备份恢复和失败保护 |
| 应用发布 | 对应平台正式签名构建、版本及签名检查、真机验收和发布记录 |

真机验收包含安装、记账、编辑、删除、统计、备份恢复、系统文件选择器、杀进程或重启后的持久化，以及覆盖升级。界面变化还需检查小屏、字体放大、安全区域和键盘。

验证记录写明源码提交、平台、应用版本、构建号、设备型号、系统版本及结果。没有测量数据时，不承诺帧率、功耗或冷启动性能。缺少工具链或设备时，列明未完成项及原因，不将跳过写成通过。

## 签名、安全与发布

仓库公开，自有代码采用 MIT 许可证。协作者保持现有权限，不扩大权限。不得提交真实账本、JSON 或 CSV 备份、签名密钥、密码、令牌、机器专用配置或构建缓存。

官方 Android 升级包保持原签名。iOS 接入后，维护正式应用标识和签名配置，验证升级与本地数据保留。签名材料通过仓库外的安全方式管理。

缺少正式签名材料时，不得把测试签名包当作官方升级包。当前 Android 工程缺少发行签名时会使用调试签名，正式发布前必须检查产物签名。本规范不代表已经修改构建配置。

应用版本完成检查后，及时提交并推送公开仓库 `ace865/jianzhang`。应用发布按以下步骤执行：

1. 确定产品版本与构建号，更新 `pubspec.yaml` 和变更记录。
2. 完成对应平台检查、正式签名构建和真机验收，记录未完成项。未完成必要验收时，保留测试状态，不宣称正式支持。
3. 固定源码提交，创建 `v产品版本` 标签，例如 `v1.3.0` 或 `v1.3.0-beta.1`。标签不包含构建号；同版本标签已存在时复用，确认源码提交一致，不移动标签。
4. 用标签对应提交构建安装包和源码包。检查版本、签名和文件摘要，确认附件与源码一致。
5. 发布到 Releases，列明各平台版本、构建号、验证结果和分发状态。安装包与源码 ZIP 作为附件，不提交到源码历史。

新附件使用包含平台、产品版本和构建号的文件名，例如 `jianzhang-android-1.3.0-build11.apk`。源码包使用 `jianzhang-1.3.0-source.zip`，记录对应提交；源码为两端共用时无需重复打包。

已有标签和附件不覆盖，不强制推送，不删除历史。重发构建增加构建号，并使用新的附件名；历史发布材料保留原样。正式支持 iOS 后，两端同一产品版本允许不同日期发布，使用同一标签对应源码，发布记录明确另一端是待发布、已发布还是受阻。

当前应用商店发布不在授权范围内。iOS 安装包或测试渠道分发也需具备实际签名与分发条件。没有授权连接时，说明未上传的内容与原因。
